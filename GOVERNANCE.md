# How the EquiPop team works

**Who decides what, and how a piece of work becomes part of EquiPop.**
[CONTRIBUTING.md](CONTRIBUTING.md) says how to do the work; this file says how it is decided.
*Proposed 13 November 2026 for the board's first meeting. Nothing here is in force until the board merges it, and it changes the way everything else does: by pull request.*

---

## 2. Areas

An area is a set of folders with one owner and one backup. **Inside your area you work without asking; outside it, you ask first.** GitHub reads the areas from `.github/CODEOWNERS` and asks the area owner to review every pull request that touches the area.

## 3. A new tool, from idea to release

The example is a regression tool with a Stata door first and QGIS and Pro later. The steps are the same for any tool.

1. **Proposal.** The developer opens a *New tool* issue. It says what the tool computes and for whom, the method and its sources, which doors come first, how the tool will be validated, and which shared files it will need (CONTRIBUTING.md, section 9). The board accepts, changes or declines it. Once accepted, the tool gets an area label (`area:regress`), an owner and a backup.
2. **Its own files.** Everything the tool is lives in files nobody else edits:
   - engine: `equipop/regress/`, a Python package taking numbers in and giving numbers out. The number is computed once, here, and the doors only collect the question and show the answer.
   - tests: `tests/test_regress_*.py`
   - Stata door: `stata/equipop_regress.ado`, with its help generated by `tools/make_sthlp.py`
   - QGIS door: `qgis/equipop_qgis/alg_regress.py`
   - Pro door: see step 5
   - notes: `docs/tools/regress.md`, copied from `docs/tools/TEMPLATE.md`

   Once the engine is in main, every other part of EquiPop can import it.
3. **Small pull requests, one a week or so.** Do not keep one big branch open for months. Make one issue, one branch and one pull request per step: the core estimator, then the standard errors, then the Stata door. Each is merged when the board accepts it. A branch that lives for months drifts away from main and comes back as a merge nobody can review.
4. **Experimental until promoted.** A new tool is in main from its first merge, marked **experimental**. The Python package warns when it is imported, each door puts "(experimental)" in the tool's name, and MANUAL.md says so. People can try it in a release, and nobody mistakes it for finished. **Promotion to standard is a board decision**, taken when the checks in section 4 are complete.
5. **Wiring last, and small.** Registering the tool in the shared files is one small pull request of its own, reviewed by the owner of those files. Those files are `dispatch()` in `stata_bridge.py`, the QGIS provider, `stata.toc` and `equipop.pkg`. The Pro toolbox is one file of about 6,000 lines (`arcgis/EquiPop.pyt`). How a second developer's tool goes in without editing that file is an open question, to be settled before the first Pro door of a new tool is built.

## 4. What the board checks

A pull request comes to the board when it is marked *Ready for review* and labelled `board`, by the day before the meeting. The board looks at:

- **The checks.** All nine required checks must be green; GitHub merges nothing otherwise.
- **Validation as tests.** These are reference results that anyone can rerun. For a regression: the same model on the same data in an established program (Stata's own `regress`, R, statsmodels), with coefficients and standard errors agreeing to a stated tolerance. They go in as tests, so they are checked on every push from then on, not once.
- **Door parity.** Each door gives the engine's numbers, as `tests_real_qgis/` does for QGIS.
- **A hand check** in the programs CI cannot run (Stata, Pro), by the area owner or a board member. Use the files from the pull request's own CI run: the *tests* run page → *Artifacts* → the `equipop-…` download.
- **What moves.** The pull request's *Numbers that change* and *Runs that now stop*, and its note in `changes/`.
- **Method decisions.** These go on their own issue (template *Method decision*) and are ruled before the code that depends on them.

For each item the board decides **merge**, **merge as experimental**, **revise** (saying what) or **decline** (saying why).

**Not everything waits for the board.** A fix or a document change inside one area that changes no numbers and stops no runs can be reviewed and merged by the area owner on any day. Everything else goes to the board: a new tool, a method decision, changed numbers, newly refused runs, the shared files, a release.

## 5. The weekly meeting

- **The agenda** is an issue opened from the *Board meeting* template. It lists everything open with the label `board`; on the Issues and Pull requests tabs, the search `is:open label:board` finds them.
- **Decisions** are written as a comment on each item ("Board 20 Nov: merge as experimental") and summed up in the meeting's issue, which is then closed. A method decision also becomes a RULINGS.md entry, by pull request.
- **After the meeting**, the area owner merges what was accepted with *Squash and merge*.
- **Releases** are decided at a meeting: what goes in, what stays experimental, who does the hand checks. John builds the release, and an owner approves the upload to PyPI (CONTRIBUTING.md, section 6).

## 6. Where things are written down: one place for each kind

| What | Where |
|---|---|
| Ideas, bugs and tasks (the backlog) | **GitHub issues**, each with an area label. The meeting's agenda is the label `board`. |
| Who is working on what | the issue's **assignee**, and a **draft pull request** opened on the first day |
| Method decisions | **RULINGS.md** |
| Other decisions | a comment on the pull request or issue, and the meeting's issue |
| What a release changes | one note per pull request in **`changes/`**, gathered into **MANUAL.md**'s version table at release |
| How a tool works, its status, and where the work stands | **`docs/tools/<tool>.md`** |
| Everything up to 13 November 2026 | **BACKLOG.md** (entries 1 to 502) and the HANDOVER files, kept as they are |

**Why issues, and not BACKLOG.md, for new work.** BACKLOG.md works for one person: one file, with numbers handed out in order. With five people it fails in two ways.
- Two people writing on the same day both take entry 503.
- Every new entry is an edit at the same place in the same file, so every pull request conflicts with every other.

GitHub numbers issues itself, so numbers never collide. Issues can be assigned, labelled and searched, and they close themselves when the pull request that fixes them is merged ("Fixes #42" in its description). The BACKLOG keeps everything up to entry 502, and those numbers stay valid references.

*`#42` is an issue or pull request; `BACKLOG 42` is an entry; `R-42` is a ruling.*
